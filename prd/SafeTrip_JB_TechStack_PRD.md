# SafeTrip JB — Tech Stack PRD

**문서 버전**: v0.1 (Draft)
**작성일**: 2026-07-21
**관련 문서**: SafeTrip JB 서비스 기획, 전라북도 방문자 분석 API Design System PRD
**작성 목적**: SafeTrip JB 서비스(웹/앱 + 방문자 분석 API + AI 분석 기능)를 구축하기 위한 기술 스택을 정의하고, 각 스택 선택의 근거를 서비스 요구사항과 연결하여 개발팀이 일관된 기준으로 구현하도록 한다.

---

## 1. 문서 개요

### 1.1 배경
SafeTrip JB는 ① 다중 사용자(관광객, 교통기관, 축제 운영본부)를 대상으로 한 대시보드형 웹/앱 서비스, ② 전북 시·군별 방문객·축제·기상 데이터를 통합하는 방문자 분석 API, ③ 방문객 증감 원인을 설명하는 AI 분석 기능, ④ 외부 데이터 제공기관(한국관광공사, 기상청, 공공데이터포털) 연동이라는 4개의 축으로 구성된다.

이 문서는 위 구성요소를 구현하는 데 필요한 기술 스택을 계층별로 정의한다.

### 1.2 목적
- 서비스 요구사항(실시간성, 데이터 신뢰성, 다중 사용자 권한, AI 분석)에 맞는 기술을 선정한다.
- 팀 내 기술 합의를 문서화하여 신규 합류 개발자의 온보딩 기준으로 활용한다.
- MVP와 확장 단계의 스택을 구분하여 과설계를 방지한다.

### 1.3 범위
포함: 프론트엔드, 백엔드, 데이터베이스, 데이터 파이프라인, AI/분석 계층, 인프라·배포, 인증/보안, 모니터링, 외부 연동
제외: 상세 UI 디자인 시스템(별도 문서), 조직/인력 계획

## 2. 전체 아키텍처 개요

```
[외부 데이터 제공기관]
  한국관광공사 / 기상청 / 공공데이터포털
              │  (배치 수집, REST/Open API)
              ▼
      [데이터 수집 파이프라인]
              │
              ▼
      [데이터 저장소: PostgreSQL + TimescaleDB]
              │
              ▼
   [방문자 분석 API 서버 (Backend)]
        │              │
        ▼              ▼
  [AI 분석 모듈]   [캐시: Redis]
        │              │
        └──────┬───────┘
               ▼
        [API Gateway / BFF]
               │
        ┌──────┴──────┐
        ▼             ▼
   [웹 프론트엔드]  [모바일 앱]
   (관광객/기관/운영본부 화면 분기)
```

## 3. 프론트엔드

| 항목 | 선택 기술 | 선정 근거 |
|---|---|---|
| 웹 프레임워크 | Next.js (React 기반) | 대시보드형 UI(그래프, 지도, 지수 카드)와 SEO가 필요한 소개 페이지를 동시에 지원 |
| 상태 관리 | TanStack Query + Zustand | 서버 상태(방문객 추이, 혼잡 지수 등)는 TanStack Query로 캐싱, 클라이언트 UI 상태는 Zustand로 최소화 |
| 스타일링 | Tailwind CSS | 포화상태(안전/보통/주의/혼잡) 등 상태 기반 색상 시스템을 유틸리티 클래스로 빠르게 구현 |
| 데이터 시각화 | Recharts / D3.js | 14일 방문객 추이 선 그래프, 혼잡 지수 게이지 등 커스텀 시각화 |
| 지도 | Kakao Map API 또는 Naver Map API | 국내 지도 데이터 정확도 및 전북 지역 상세 데이터 지원 |
| 모바일 앱 | React Native (Expo) | 웹과 로직/컴포넌트 일부 공유, MVP 단계에서 개발 리소스 절감 |
| 국제화 | next-intl (확장 단계) | 향후 다국어 지원 대비 |

## 4. 백엔드

| 항목 | 선택 기술 | 선정 근거 |
|---|---|---|
| 언어/프레임워크 | Node.js (NestJS) 또는 Python (FastAPI) | NestJS: 모듈화된 구조로 사용자 그룹별(관광객/기관/운영본부) 권한 분리 용이. FastAPI: AI/데이터 분석 로직과 언어 통일 시 유리. **MVP는 FastAPI 단일 스택 권장** (AI 분석 파트와 동일 언어로 개발 속도 확보) |
| API 설계 | REST (OpenAPI 3.0 스펙 기반) | 「전라북도 방문자 분석 API Design System PRD」의 리소스 구조를 그대로 구현 |
| 인증 | OAuth 2.0 + JWT | 사용자 그룹별(Public/기관/관리자) 차등 권한 부여 |
| 백그라운드 작업 | Celery (Python) 또는 BullMQ (Node) | 일별 방문객 데이터 수집, 혼잡 지수 재계산 등 배치 작업 처리 |
| API 문서화 | Swagger (OpenAPI) 자동 생성 | Design System PRD의 엔드포인트 정의와 실제 구현 간 정합성 유지 |

## 5. 데이터베이스 및 저장소

| 항목 | 선택 기술 | 선정 근거 |
|---|---|---|
| 주 데이터베이스 | PostgreSQL | 지역/축제/사용자 등 관계형 데이터 구조에 적합, 트랜잭션 안정성 |
| 시계열 데이터 | TimescaleDB (PostgreSQL 확장) | 14일 이상의 일별 방문객 수, 혼잡 지수 등 시계열 데이터의 효율적 저장·집계 |
| 캐시 | Redis | 지역 대시보드, 혼잡 지수 등 자주 조회되는 응답 캐싱으로 응답 속도 개선 |
| 객체 스토리지 | AWS S3 (또는 국내 리전 대응 시 NCP Object Storage) | 축제 운영본부용 리포트(CSV/Excel export) 및 원본 수집 데이터 백업 저장 |
| 검색(확장 단계) | Elasticsearch | 지역/축제명 검색 기능 고도화 시 도입 |

## 6. 데이터 파이프라인

| 항목 | 선택 기술 | 선정 근거 |
|---|---|---|
| 수집 스케줄링 | Apache Airflow (또는 초기엔 Cron + Celery Beat) | 한국관광공사·기상청·공공데이터포털의 일/시간 단위 배치 수집 관리, 실패 재시도 |
| ETL 처리 | Python (Pandas / Polars) | 원본 데이터를 표준 스키마(방문객 수, 축제, 기상)로 정제·결합 |
| 데이터 검증 | Great Expectations (확장 단계) | 데이터 결측·이상치 검증 후 `is_estimated` 플래그 결정에 활용 |
| 메시지 큐 (확장 단계) | Kafka 또는 Redis Streams | 실시간성이 요구되는 혼잡 알림(Webhook) 기능 도입 시 |

## 7. AI / 분석 계층

| 항목 | 선택 기술 | 선정 근거 |
|---|---|---|
| AI 원인 분석 | Anthropic Claude API (Claude Sonnet 계열) | 방문객 증감 원인을 자연어로 설명하는 「AI 원인 분석 화면」 요구사항 충족, 데이터 출처를 함께 근거로 제시하는 프롬프트 설계 용이 |
| 프롬프트 관리 | 자체 프롬프트 템플릿 저장소 (버전 관리) | 지역/사용자 그룹별 분석 톤 차별화 (관광객용 요약 vs 운영본부용 상세 리포트) |
| 혼잡 지수 예측 모델 | scikit-learn 기반 회귀 모델 (MVP) → 필요시 시계열 모델(Prophet) 확장 | 방문객 수, 요일, 축제 여부, 날씨를 입력으로 혼잡 지수 추정 |
| 모델 서빙 | FastAPI 내 동일 서비스로 통합 (MVP) → 별도 추론 서버 분리 (확장 단계) | 초기에는 별도 인프라 없이 백엔드와 통합하여 운영 비용 절감 |

## 9. 인증 · 보안

| 항목 | 선택 기술 | 선정 근거 |
|---|---|---|
| 인증 프로토콜 | OAuth 2.0 + JWT | 「Design System PRD」에서 정의한 사용자 그룹별(Public/기관/관리자) 접근 제어 구현 |
| 비밀 관리 | AWS Secrets Manager | 외부 API 키(기상청, 공공데이터포털 등) 안전한 관리 |
| API 보호 | Rate Limiting (Redis 기반) + WAF | 공개 API 키의 초당 요청 제한 및 악성 트래픽 차단 |
| 개인정보 | 방문객 수는 집계 데이터만 사용 (비식별화) | 개인 위치·이동 데이터를 직접 수집하지 않고 공공 통계 기반 집계치만 활용 |

| Anthropic Claude API | AI 원인 분석 텍스트 생성 | 데이터 출처를 프롬프트 컨텍스트로 포함하여 신뢰성 확보 |

## 12. 단계별 기술 스택 로드맵

### MVP (1차 출시)
- Frontend: Next.js + Tailwind + Recharts
- Backend: FastAPI 단일 서비스 (API + AI 분석 통합)
- DB: PostgreSQL + TimescaleDB, Redis 캐시
- 배치 수집: Cron + Celery
- 인프라: AWS ECS Fargate + GitHub Actions
- AI: Claude API 직접 호출

### 확장 단계 (트래픽/기능 확대 시)
- 백엔드 서비스 분리: API 서버 / AI 추론 서버 / 데이터 파이프라인 서버
- Airflow 기반 파이프라인 고도화, Kafka 도입 검토
- Kubernetes(EKS) 전환
- Elasticsearch 기반 검색 고도화
- 다국어 지원 및 Webhook 알림 기능

| 리스크 | 내용 | 대응 방안 |
